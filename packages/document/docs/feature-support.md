# Document Feature Support

This matrix describes the public `@pptx-glimpse/document` surface. It is intentionally
separate from SVG/PNG rendering fidelity: a value can be available in the document model
without being rendered by `pptx-glimpse`.

## Status legend

- **S — supported**: a typed public workflow exists for this stage and is covered by an
  implementation test. This does not mean that every OOXML variant is supported.
- **△ — partial**: typed support exists, but only for the constraints described below.
- **P — preserved**: there is no typed workflow for this stage, but unchanged source material is
  retained as a raw sidecar or raw package part for structural round trips.
- **— — unsupported**: neither a typed workflow nor a preservation guarantee is currently
  documented and tested.

“Existing edit” means changing or deleting an element already present in an input PPTX. Adding a
new element to a slide loaded from an existing PPTX uses the same authoring operations as the
from-scratch writer and is therefore represented in the “from-scratch writer” column instead.

“Round-trip preservation” is structural, not byte-for-byte. `P` in that column means no-edit,
opaque preservation only; `S` means supported edits or typed authoring are also written and
reread in tests. See [Writing and round-trip preservation](./writing.md).

Consecutive authoring can be coordinated through the public `createPptxAuthoringSession` API.
Its target scopes delegate to the same immutable authoring functions documented below and return
the `SourceHandle` of each newly added drawing or slide. The public `reorderShapes` operation (also
available on target scopes) sets the complete top-level drawing order for a slide, layout, or
master after additions, including placing a connector behind its connection targets.

|
| Text                    | The reader and computed view expose typed paragraphs, runs, body properties, and the supported style cascade. Authoring covers text boxes and shape/table text with the typed formatting inputs shown in [Authoring a PPTX from scratch](./authoring.md). Existing shape text and Table cell text share the public plain run/paragraph text, selected run properties, and paragraph alignment/level/bullet operations. See [writer edit tests][writer-tests] and [Table cell text edit tests][table-text-edit-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Shape                   | Common transforms, preset/custom geometry, fills, outlines, text, and selected effects are typed; unmodeled DrawingML remains raw. Authoring accepts the inputs defined by `AddShapeInput`; `reorderShapes` changes the complete top-level drawing order when every target has a node id, preserves non-drawing `p:spTree` children in place, and rejects `mc:AlternateContent` shape trees. Existing slide transform, fill, and outline edits resolve conforming top-level or nested group nodes by the part-local `(partPath, nodeId)` identity and patch only the owning slide part. `orderingSlot` is the handle-comparison and preservation fallback when no node id exists, but these property edits require `nodeId` for both top-level and nested targets. Duplicate ids and `mc:AlternateContent` descendants are rejected rather than guessed. Group/ungroup can move consecutive siblings at the root or within a group while preserving child ids and handles. Delete and reorder remain top-level-only operations and explicitly reject nested targets. See [shape authoring][shape-authoring], [shape ordering][shape-ordering], [shape grouping][shape-grouping], [shape editing][shape-editing], [writer edit tests][writer-tests], and [typed reader tests][reader-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Picture                 | Typed reading/computation resolves embedded media, crop, stretch/tile mode, and supported picture/effect properties. Authoring is limited to PNG/JPEG bytes and the typed crop/effect inputs. Existing replacement preserves the media content type: a singly referenced part is updated in place, while a shared part uses copy-on-write with a collision-free media path and relationship so only the selected picture changes. The edit journal reserves allocated paths; undo/redo restore the corresponding snapshots, and no orphan sweep is needed for this operation. Existing crop editing accepts integer OOXML percentages (`100000` = 100%) in `0..100000`, requires each opposing-edge sum below `100000`, rejects rather than clamps invalid values, and supports only slide pictures with exactly one `a:stretch` and no `a:tile`. Set/clear operations patch only the targeted `a:srcRect`, preserve sibling/unknown XML and media bytes, and detect effective no-ops. See [picture authoring][picture-authoring], [picture crop editing][picture-crop-editing], [image replacement][image-replacement], [writer edit tests][writer-tests], [editor command tests][editor-command-tests], and [core editor tests][core-editor-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Connector               | Typed source/computed nodes retain supported transforms, geometry, outlines, connection sites, and arrow endpoints. Authoring uses the connector presets, endpoint forms, and horizontal/vertical transform flips accepted by `AddConnectorInput`. Existing connectors can use the supported outline and delete operations, but there is no endpoint/geometry editing API. See [shape authoring][shape-authoring], [shape editing][shape-editing], and [writer edit tests][writer-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Table                   | Native tables have typed rows, columns, cells, text, fills, borders, margins, merges, and hyperlinks for the implemented subset. Existing cell paragraphs and runs support the same public text operations as shape text. Existing physical cells are addressed by Table handle plus zero-based row/cell indices; inline fill (`none` or solid sRGB), four-side border width/fill, and four margins can be set or cleared to inheritance. Dirty writes patch only the targeted cell text or `a:tcPr` values and preserve text, merges, sibling cells, unknown cell XML, and surrounding Table XML. Row/column topology, merge/unmerge, diagonal or advanced line styles, and table-style definition editing remain unsupported. See [table authoring][table-authoring], [Table cell text edit tests][table-text-edit-tests], [Table cell property edit tests][table-cell-property-edit-tests], and [reader tests][reader-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Chart                   | The reader/computed view supports typed chart relationships and data projections for bar, line, pie, doughnut, area, scatter, bubble, radar, stock, surface, and of-pie charts; other chart XML remains preserved package material. Authoring is narrower: `addChart` creates bar, line, pie, area, doughnut, or radar charts with an editable embedded workbook and the typed formatting implemented in [chart authoring][chart-authoring]. Existing category charts of those six types can use `updateChartData` when they have one internal, unshared embedded workbook, one worksheet, and the standard row-1 names / column-A categories / column-B-onward values layout. The operation can append or truncate trailing series and replaces names, string/number caches, formulas, point counts, worksheet range, and target cells together. Retained positional series preserve their formatting, unknown XML, and `idx` / `order`; additions clone the last original series as their formatting template, receive values after the largest existing `idx` / `order`, and regenerate cloned `c16:uniqueId`; deleted series take their owned formatting/unknown XML with them. Chart type, axes, title, legend, chart-level unknown XML, and unrelated workbook parts are preserved. Series removal with explicit legend entries is rejected because their index semantics vary by chart type. External or shared data, combo Charts, unresolved relationships, formulas or cells outside the chart data range, and other layouts are rejected. See [chart data editing][chart-data-editing] and its public-root integration tests.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Group                   | Group `off` / `ext` / rotation / flips and `chOff` / `chExt` remain source-local and children retain immediate-parent coordinates in the recursive source/computed tree. The renderer boundary composes ancestor transforms; incomplete child transforms use a warning-backed `chOff=(0,0), chExt=group ext` display fallback, while zero `chExt` axes remain typed and render with identity scale for that axis. Existing groups with a conforming node id and authored transform can use the public transform edit, including when nested, and supported child property edits use the same recursive locator. `groupShapes` replaces consecutive siblings under one root/group parent with an identity-mapped native group; `ungroupShape` expands only identity-mapped groups without group appearance/unknown XML. The authoring session exposes the same operation after generic shape/text, PNG/JPEG picture, connector, native Table/Chart graphic-frame, or native-group creation; slide/layout/master and native-group targets share the direct-child container contract. Headless and integrated editor commands select the new group after grouping and the first child in document order after ungrouping, with topology/selection restored by undo/redo. These operations preserve child ids/handles/order and internal connector ids, and reject crossing/dangling connector references, ambiguous ids, unsupported topology, and non-lossless mappings atomically. Arbitrary affine ungroup, SmartArt/raw-node authoring, connector rerouting, group fill editing, nested delete, and nested reorder remain unsupported. See [authoring guide](./authoring.md#native-groups), [authoring session tests][authoring-session-tests], [shape grouping][shape-grouping], [editor command tests][editor-command-tests], [core editor tests][core-editor-tests], [computed view types][computed-types], [reader tests][reader-tests], [computed view tests][computed-view-tests], [writer edit tests][writer-tests], and [renderer group tests][renderer-group-tests]. |
| Background              | Slide/layout/master fallback and the implemented fill/style-reference subset are typed; unmodeled backgrounds stay raw. The public handle-based `setBackground` / `clearBackground` API edits existing slides, layouts, and masters with solid sRGB, linear/radial gradient, PNG, JPEG, or direct-background removal; `setSlideBackground` remains as a slide-only compatibility API. Image edits add target-owned media relationships without deleting replaced raw relationships/media, and background patching preserves unrelated raw siblings/sidecars while intentionally replacing unsupported content inside the targeted `p:bg`. Core scopes layout/master background rerenders to slides whose effective fallback changes. See [background editing](./authoring.md#editing-existing-backgrounds), [background authoring](https://github.com/hirokisakabe/pptx-glimpse/blob/main/packages/document/src/source/slide-background-authoring.ts), [writer edit tests][writer-tests], and [core editor tests][core-editor-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Master / layout / theme | The reader exposes presentation masters in `p:sldMasterIdLst` order through `SourcePresentation.slideMasterPartPaths`, each master's layouts in `p:sldLayoutIdLst` order through `SourceSlideMaster.layoutPartPaths`, and layout visibility through `SourceSlideLayout.show`; missing id-list relationships produce diagnostics, while packages without an id list fall back to relationship order. The reader and computed view follow the slide → layout → master → theme chain and expose the implemented background, placeholder, color-map, color/font scheme, and text-style semantics. `createPptx` can configure its single theme name, all 12 sRGB color-scheme slots, and the major/minor Latin, East Asian, and complex-script font scheme; every field is optional and receives a documented default. `addSlideLayout` and `PptxAuthoringSession.addSlideLayout` append an empty layout to an existing master with typed name, OOXML type, visibility, solid/PNG/JPEG background, and authoring-only default text margins; package part paths, content types, relationships, numeric IDs, and `layoutPartPaths` order are allocated together. The immutable function returns the updated source, while the session method returns a handle that accepts the existing drawing APIs and can create slides through `addEmptySlideFromLayout`. Additional masters, layout duplication, placeholder authoring, existing-theme editing, and format-scheme authoring remain unsupported. No-edit round trips preserve existing master/layout order, while authored layouts and themes are covered by public-root write/read/computed/render and LibreOffice validity tests. Existing template/theme parts are otherwise retained as opaque package material. See [authoring guide](./authoring.md#theme-colors-and-fonts), [layout authoring][layout-authoring], [presentation reader tests][presentation-reader-tests], [writer edit tests][writer-tests], [computed view][computed-view-source], and [builder][builder-source].                                         |

The raw preservation hooks and dependency boundaries behind the final column are documented on
[`PptxSourceModel`][source-model] and in the [`writePptx` implementation][writer-source]. If a
capability is not supported by a public root export and confirmed by implementation tests, this
table must not mark it `S`.
