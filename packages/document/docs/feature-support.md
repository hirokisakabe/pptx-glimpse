# Document Feature Support

This matrix describes the public `@pptx-glimpse/document` surface. It is intentionally
separate from SVG/PNG rendering fidelity: a value can be available in the document model
without being rendered by `pptx-glimpse`.

## Status legend

- **S — supported**: a typed public workflow exists for this stage and is covered by an
  implementation test. This does not mean that every OOXML variant is supported.
- **△ — partial**: typed support exists, but only for the constraints described below.
- **P — preserved**: there is no typed workflow for this stage, but unchanged source material is
  retained as a raw sidecar or raw package part for structural round trips.
- **— — unsupported**: neither a typed workflow nor a preservation guarantee is currently
  documented and tested.

“Existing edit” means changing or deleting an element already present in an input PPTX. Adding a
new element to a slide loaded from an existing PPTX uses the same authoring operations as the
from-scratch writer and is therefore represented in the “from-scratch writer” column instead.

“Round-trip preservation” is structural, not byte-for-byte. `P` in that column means no-edit,
opaque preservation only; `S` means supported edits or typed authoring are also written and
reread in tests. See [Writing and round-trip preservation](./writing.md).

Consecutive authoring can be coordinated through the public `createPptxAuthoringSession` API.
Its target scopes delegate to the same immutable authoring functions documented below and return
the `SourceHandle` of each newly added drawing or slide. The public `reorderShapes` operation (also
available on target scopes) sets the complete direct-child drawing order for a slide, layout,
master, or native group after additions, including placing a connector behind its connection
targets.

| Shape                   | Common transforms, preset/custom geometry, fills, outlines, text, and selected effects are typed; unmodeled DrawingML remains raw. Authoring accepts the inputs defined by `AddShapeInput`; `reorderShapes` changes the complete direct-child drawing order for slide/layout/master roots or native groups when every target has a node id, preserves non-drawing children in the selected container, and rejects duplicate ids and `mc:AlternateContent` shape trees. Existing slide, layout, and master property editing supports transforms on typed drawing nodes with `xfrm`, fill on `p:sp`, and outline on `p:sp` / `p:cxnSp`. These edits resolve conforming top-level or nested group nodes by the part-local `(partPath, nodeId)` identity and patch only the owning drawing part. `orderingSlot` is the handle-comparison and preservation fallback when no node id exists, but these property edits require `nodeId` for both top-level and nested targets. Group/ungroup can move consecutive siblings at the root or within a group while preserving child ids and handles. Public `deleteShape` accepts top-level `p:sp`, `p:cxnSp`, `p:pic`, native Table/Chart `p:graphicFrame`, and `p:grpSp`; nested child delete remains unsupported. It rejects SmartArt/raw/`mc:AlternateContent` targets and any deletion subtree referenced by an external connector. Owner relationships are removed only when absent from the retained owner XML; reachable internal parts are then removed recursively only after package-wide incoming relationships reach zero, preserving shared resources, unprovable references, and unrelated orphans. Reorder supports only a single root/group parent's complete direct-child order and never moves nodes across parents. | Picture                 | Typed reading/computation resolves embedded media, crop, stretch/tile mode, and supported picture/effect properties. Authoring is limited to PNG/JPEG bytes and the typed crop/effect inputs. Existing replacement preserves the media content type: a singly referenced part is updated in place, while a shared part uses copy-on-write with a collision-free media path and relationship so only the selected picture changes. The edit journal reserves allocated paths; undo/redo restore the corresponding snapshots, and no orphan sweep is needed for this operation. Existing crop editing accepts integer OOXML percentages (`100000` = 100%) in `0..100000`, requires each opposing-edge sum below `100000`, rejects rather than clamps invalid values, and supports only slide pictures with exactly one `a:stretch` and no `a:tile`. Set/clear operations patch only the targeted `a:srcRect`, preserve sibling/unknown XML and media bytes, and detect effective no-ops. Top-level pictures also support public deletion with retained-owner relationship proof; unshared media is removed only at zero package-wide incoming references, while shared media and unprovable/raw references are preserved. | Table                   | Native tables have typed rows, columns, cells, text, fills, borders, margins, merges, and hyperlinks for the implemented subset. Existing cell paragraphs and runs support the same public text operations as shape text. Existing physical cells are addressed by Table handle plus zero-based row/cell indices; inline fill (`none` or solid sRGB), four-side border width/fill, and four margins can be set or cleared to inheritance. Dirty writes patch only the targeted cell text or `a:tcPr` values and preserve text, merges, sibling cells, unknown cell XML, and surrounding Table XML. A native top-level Table `p:graphicFrame` supports public deletion; SmartArt and unknown/raw graphic frames are rejected, and only relationships exclusively referenced by the deleted frame are eligible for cleanup. Row/column topology, merge/unmerge, diagonal or advanced line styles, table-style definition editing, and nested delete remain unsupported. | Chart                   | The reader/computed view supports typed chart relationships and data projections for bar, line, pie, doughnut, area, scatter, bubble, radar, stock, surface, of-pie, and fixed bar+line category combo charts; combo projection retains plot-group document order, authored grouping, the authored `axId` element count, populated group `axId` references, uniquely resolved category/value-axis IDs, and value-axis positions. The adapter skips unsupported grouping or inexact/incomplete/ambiguous combo axis topology with a diagnostic. The renderer uses a zero-inclusive scale for groups referencing the same value axis, draws the category baseline at the primary value-axis zero coordinate, renders a distinct right-side scale for a secondary value axis, and handles zero-only and all-negative domains. Other chart XML remains preserved package material. Authoring is narrower: `addChart` creates bar, line, pie, area, doughnut, or radar charts with an editable embedded workbook and the typed formatting implemented in [chart authoring][chart-authoring]. Existing category charts of those six types can use `updateChartData` when they have one internal, unshared embedded workbook, one worksheet, and the standard row-1 names / column-A categories / column-B-onward values layout. The same operation accepts exactly one nonempty, non-stacked `barDir=col` bar plus one nonempty, non-stacked line plot group when each authors exactly two populated `axId` elements, both use one common `catAx`, each resolves exactly one `valAx`, every input carries the computed plot-type + OOXML `idx` source descriptor, and the series count and group membership stay fixed; it updates all group caches/formulas and the shared standard worksheet while preserving group order, `idx` / `order`, axes, formatting, and unknown XML. Horizontal, stacked, empty, or inexact-axis bar+line combos are rejected atomically for editing and skipped with an unsupported renderer diagnostic. Existing scatter charts can separately use `updateScatterChartData` with paired finite X/Y values when each series occupies a standard two-column XY table (X in A, Y/name in B, one spacer row between series). Existing bubble charts use `updateBubbleChartData` with equal finite X/Y/bubble-size arrays and a standard three-column table (X in A, Y/name in B, `Size`/bubble size in C, one spacer row between series). The single-group operations can append or truncate trailing series and replace names, caches, formulas, point counts, worksheet range, and target cells together. Retained positional series preserve their formatting, unknown XML, and `idx` / `order`; additions clone the last original series as their formatting template, receive values after the largest existing `idx` / `order`, and regenerate cloned `c16:uniqueId`; deleted series take their owned formatting/unknown XML with them. Chart type, axes, title, legend, chart-level unknown XML, and unrelated workbook parts are preserved. Series removal with explicit legend entries is rejected because their index semantics vary by chart type. External or shared data, unsupported combos, unresolved relationships, multiple worksheets, formulas or cells outside the chart data range, and other layouts are rejected atomically. Top-level native Chart graphic frames also support public deletion. The owner chart relationship is removed only after retained XML proves it unused; the chart part and its embedded workbook/media dependency chain are recursively removed only when each part has zero package-wide incoming relationships. Shared charts/workbooks, unprovable references, and unrelated orphan parts are retained. Nested Chart delete remains unsupported. See [chart data editing][chart-data-editing] and its public-root, editor/core, renderer, snapshot VRT, and LibreOffice validity tests. |
| Group                   | Group `off` / `ext` / rotation / flips and `chOff` / `chExt` remain source-local and children retain immediate-parent coordinates in the recursive source/computed tree. The renderer boundary composes ancestor transforms; incomplete child transforms use a warning-backed `chOff=(0,0), chExt=group ext` display fallback, while zero `chExt` axes remain typed and render with identity scale for that axis. Existing groups with a conforming node id and authored transform can use the public transform edit, including when nested, and supported child property edits use the same recursive locator. `groupShapes` replaces consecutive siblings under one root/group parent with an identity-mapped native group; `ungroupShape` expands only identity-mapped groups without group appearance/unknown XML; `reorderShapes` replaces one group's complete direct-child z-order without changing ids, handles, transforms, or other containers. The authoring session exposes these direct-child operations after generic shape/text, PNG/JPEG picture, connector, native Table/Chart graphic-frame, or native-group creation; slide/layout/master and native-group targets share the direct-child container contract. Headless and integrated editor commands select the new group after grouping and the first child in document order after ungrouping, with topology/selection restored by undo/redo. These operations preserve child ids/handles/order and internal connector ids, and reject crossing/dangling connector references, ambiguous ids, unsupported topology, and non-lossless mappings atomically. Public deletion removes one top-level native group and its complete descendant subtree while preserving sibling order, ids, handles, and surrounding XML. Connectors outside the subtree that reference the group or a descendant reject the operation atomically; relationships and reachable parts follow the same retained-owner proof and package-wide zero-incoming cleanup rule. Nested group/child delete remains unsupported. Arbitrary affine ungroup, SmartArt/raw-node authoring, connector rerouting, group fill editing, nested delete, cross-parent reorder, and partial reorder remain unsupported. See [authoring guide](./authoring.md#native-groups), [authoring session tests][authoring-session-tests], [shape grouping][shape-grouping], [shape ordering][shape-ordering], [editor command tests][editor-command-tests], [core editor tests][core-editor-tests], [computed view types][computed-types], [reader tests][reader-tests], [computed view tests][computed-view-tests], [writer edit tests][writer-tests], and [renderer group tests][renderer-group-tests].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

| Master / layout / theme | The reader exposes presentation masters in `p:sldMasterIdLst` order through `SourcePresentation.slideMasterPartPaths`, each master's layouts in `p:sldLayoutIdLst` order through `SourceSlideMaster.layoutPartPaths`, and layout visibility through `SourceSlideLayout.show`; missing id-list relationships produce diagnostics, while packages without an id list fall back to relationship order. Placeholder-capable `p:sp`, `p:pic`, and typed or raw `p:graphicFrame` nodes retain source-local `type` / `idx` / `orient` / `sz` / `hasCustomPrompt` omission and stable handles. The computed view resolves schema defaults, slide → layout by unique effective index, then layout → master by the title/body/special type category without heuristic fallback. The public `createComputedTemplateView` root API also projects one master or layout without a source slide: layout projection resolves layout/master background, visible master normal shapes, layout shapes, and compatible placeholder inheritance while excluding all real slide content. `addPlaceholder` and the authoring session create master `title`/`body` and layout `title`/`ctrTitle`/`body`/`subTitle` definitions, reject duplicate effective indexes, and `addEmptySlideFromLayout` materializes non-special empty shells without copying prompt, transform, geometry, or style. Direct slide authoring, special placeholders, and layout reconciliation remain unsupported. Existing master/layout shapes accept the same supported property subset documented in the Shape row. `createPptx` configures its single theme. `addSlideLayout` appends a layout to an existing master; `cloneSlideLayout` clones only within the same master, shares linked resources, and rejects source layouts whose XML part has pending edits. `updateThemeScheme` edits selected color-scheme slots and major/minor Latin, East Asian, or complex-script typefaces through exactly one existing theme handle. Omitted fields, `a:fmtScheme`, unknown XML, the theme path, and master relationships are preserved; malformed or ambiguous targets are rejected atomically. Core invalidation follows every master that references the edited shared theme. Theme creation/deletion/duplication, relationship rewiring, additional masters, cross-master layout moves, and format-scheme authoring/editing remain unsupported. No-edit round trips plus authored layouts/placeholders, template projection, and existing-theme edits are covered by public-root write/read/computed/render tests and LibreOffice validity. See [template projection tests][computed-template-view-tests], [existing theme editing](./editing.md#existing-theme-color-and-font-schemes), [theme editing tests][theme-editing-tests], [native placeholders](./authoring.md#native-placeholders), [placeholder authoring tests][placeholder-authoring-tests], [layout authoring][layout-authoring], [presentation reader tests][presentation-reader-tests], [computed view][computed-view-source], and [builder][builder-source].                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
